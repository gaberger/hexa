hexa / A/B evidence

Pre-registered experiment

Does hexa make AI-written code correct and the right shape?

The same model, prompt and budget, run with and without hexa. Each run is judged by a hidden oracle the agent never saw and by the architecture grade, and each result is recorded against the model that produced it.

The comparison

Every arm gets the same prompt text, including the gate command that defines “done”. The only difference is what happens between the prompt and the result.

A · Without hexa

The agent alone in a fresh workspace. It may run tests and decides for itself when it is done. Nothing checks its work.

B · With hexa

The same model driven through hexa. A result counts only when the gate command exits 0 and the architecture grade holds at A.

C · Rules only

Arm A, with hexa’s architecture rules pasted into the prompt and no gates. This separates telling the model the rules from enforcing them.

How to run it →

The rubric

Every run writes one JSON record with all of these fields. Proportions are reported for pass/fail measures, and medians for size, cost and complexity.

Accuracy

Oracle pass
The hidden oracle passes. It runs on a copy of the workspace after the agent finishes.
False-green
The agent’s own tests pass but the oracle fails, or the shape is broken. These are counted separately.
Accepted-correct (primary)
The oracle passes, and where shape applies, the grade is ≥ A with 0 violations.

Tokens & cost

Metered the same way in every arm
A claude wrapper first on PATH logs usage and dollars for every call, whether the agent makes it or hexa does.
Per good result
$ and tokens per accepted-correct result, not just per run.

Lines of code

Size
Non-blank, non-comment lines, for source and tests separately, and the test-to-source ratio.
Change
Lines added and removed, and files changed, against the starting commit.

Complexity

Cyclomatic complexity
Mean and max per function, from lizard 1.17.13, which reads Rust, Go and TypeScript the same way.
Longest function
Shows whether passing the gates made the code larger or more tangled.

Same model, or the run is void

A run is voided if any call asked for a different model, another model served calls, a call went unmetered, or the transcript touched oracle material. Voided runs are listed, never deleted.

Self-test

Before any model run, the rubric has to show it can tell right from wrong. It makes no model calls and costs nothing.

✓
5 of 5 oracles fail the untouched starting code. A test that passes before any work proves nothing.
✓
A known-correct answer passes its oracle (header-safe-url, 5 of 5 tests).
✓
The runner refuses to start unless both checks hold.

Found before the first run

Problems that would have skewed the comparison, found while reviewing the protocol and building the harness.

Fixture An oracle contradicts its own test name

header-safe-url says code points “above U+00FF” are rejected, but it also rejects é (U+00E9). An agent that follows the stated rule fails.

Grading Single-file fixtures always grade F 0

The five change fixtures have no layers to grade. That family is scored on the oracle alone. Otherwise accepted-correct would be 0 in every arm.

Leakage The hidden oracles live in the repo

Every fixture’s oracle test is in docs/benchmarks/fixtures, so tasks run in a separate workspace and transcripts are checked for oracle access.

Model “Same model” has to be enforced

hexa tries local models before Claude by default, and its text-mode path passes no --model. The wrapper pins every call and voids runs that drift.

Reproduce it

The runner, the rubric and the raw run JSON are published together.

pip install lizard==1.17.13          # plus bun, jq, the claude CLI and a built hexa
bench/ab/selftest.sh                 # no model calls
MODELS="<model id> <model id>" ARMS="A B C" RUNS=5 bench/ab/run_matrix.sh
python3 -I bench/ab/report.py bench/ab/runs
