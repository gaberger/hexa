# ADR-2609221900: What generated this is written when it is generated

**Status:** Accepted
**Date:** 2026-09-22
**Drivers:** The six example projects record their test counts and nothing about what produced them — no model, no provider, no date, no version of hexa. That is not in the repository or in its git history, so the question "which model wrote these?" has no answer on file. An article citing them as evidence of what the tool produces cannot answer the first follow-up question it will get.

## Context

The examples are the most concrete evidence this project has: working programs, with passing gates, in three languages. They are also the least attributable. A reader asking what wrote them gets nothing, and neither does the author — the information was never recorded, so no amount of searching recovers it.

Two ways to close a gap like this. Reconstruct it, or make it impossible to reopen. Reconstruction fails here: the runs are gone, the container that made them is gone, and a guess wearing a date would be worse than the silence, because it would look like a record.

So the fix is upstream of the artefact. A build that produces code should say what produced it, at the moment it produces it, in the directory it produces. Provenance written later is testimony; provenance written during is a receipt.

What the runner actually knows is narrower than what a reader might assume, and the record has to be honest about the difference. `BuildReport` carries the design and critique counts and whether the gate passed. It does not carry, per call, which model answered — the tiers resolve at dispatch, and a call that fell back to another tier is not distinguished from one that did not. Recording "this was written by model X" would therefore be a claim the runner cannot support, which is the failure mode this project has spent its own documentation on: a confident record that is wrong in a way nobody can see.

## Decision

1. **`hexa build` writes `PROVENANCE.md` into the target it generates.** At the end of the run, whether or not the gate passed. A failed build that records what it attempted is more useful than no record.

2. **It records what the run knows**, and nothing beyond it:
   - the date, in UTC, and the version of hexa that ran;
   - the challenge as given, and the gate command as given;
   - whether the gate passed;
   - the designs and critiques the run produced;
   - the models the run *resolved*: each configured tier with the model it mapped to, and the do-loop's candidate list, read at the moment of the run.

3. **It states what it does not know.** The record says in its own text that it lists the models the run resolved, not the model that answered each call, and that a call falling back to another tier is not distinguished. A reader must be able to see the limit of the claim without reading the source that produced it.

4. **No model name is written into source.** The names in the record are values read from configuration at run time through `hexa-infer`, which is where founding goal G1 requires them to come from. A provenance file is data the run produced, not a source file naming a provider.

5. **The record is generated, so it is generated by a pure function.** `provenance::record(…) -> String` takes what the run knows and returns the document; the writer only puts it on disk. This is what makes it testable without a model, a network, or a build.

## Consequences

- **New examples carry provenance; the existing six do not.** This ADR does not backfill them. They can only be regenerated, which needs a machine with models configured — no tier resolves in the environment this was written in. Until then the evidence page says what is true: the six record test counts, not provenance.
- **A record that understates is the point.** It will say "these tiers resolved to these models" rather than "this model wrote this code". That is less satisfying and is the only version that is true.
- **`PROVENANCE.md` sits in the generated project's root**, beside the README a generated project already carries. It is the generated project's own file, not this repository's.
- **The file is small and will be committed with the example.** That is the intent: it travels with the artefact, and a reader who has the directory has the answer.

## Implementation

- `hexa-exec/src/provenance.rs`: `record(Facts) -> String`, pure; `write(dir, Facts)`, the one side effect.
- `hexa-cli/src/commands/build.rs`: gather the facts after the run and write the file.
- `docs/EVIDENCE.md`: the examples entry says provenance is recorded from this version forward, and that the existing six predate it.

**Gate:** `cargo test -p hexa-exec --test provenance_is_recorded`, written first. A record names the date, the hexa version, the challenge, the gate and the outcome; it lists the resolved tiers; it states its own limit; it never omits the limit even when every tier resolved; and a run with no tiers resolving still produces a record that says so rather than an empty file.
