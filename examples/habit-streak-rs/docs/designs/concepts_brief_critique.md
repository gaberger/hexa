# Critique of the concepts brief

Brief: `docs/designs/concepts_brief.md`
Reviewer: persona `design_critic`, standard `heilmeier-standard`, on `claude-text`
Written by hexa design brainstorm, from the Elephant-Goldfish Model (EGM, https://github.com/google/elephant-goldfish-model, Google LLC, Apache-2.0) at commit a8380ab5f0aba392c97e31c79f9a6666b3f09f14
Unresolved paths (outside the project or not found; not read): `main.rs`, `$XDG_DATA_HOME/habit-streak/habits.json`, `~/.local/share/...`, `/egm-draft`

- C-1: **Major: Heilmeier "Timeline" is unanswered.** *Scope:* whole document; *Key Decisions & Staging*. The brief has no estimate of duration, milestones, or ordering. Staging only says "ADR before code" and "gate before code." *Recommendation:* add a timeline, for example ADR, then domain and oracle tests, then JSON adapter, then CLI and end-to-end. Give each step a rough effort and a target date.
- C-2: **Major: "Metrics & Exams" has a final exam but no mid-term exam and no outcome metric.** *Scope:* *Gate to record before any code*. The gate is a single pass/fail at the end. It never says when the domain is "done" before adapters exist. It also never says how the person will judge success after release, even though section 1 says the tool must beat "a text file and a script." *Recommendation:* define a mid-term exam, such as the domain `streaks` property tests passing against the oracle before any adapter code. Define a final outcome check, such as daily use for N weeks with no hand edits needed, or a stated architecture-practice learning goal met.
- C-3: **Major: "Cost" covers runtime cost but not effort.** *Scope:* §8 *Cost and scale*, §1. The standard asks for resources and headcount. §1 calls opportunity cost the deciding factor but never estimates it. *Recommendation:* state the expected person-hours, so the YAGNI trade-off in §1 can be judged.
- C-4: **Major: Exit code 2 conflicts with `clap`'s default.** *Scope:* §7 *Errors and exit codes*; §9 *Argument parsing*. `clap` exits with code 2 on usage and parse errors. Under §7, a bad flag would then look like "data file problem," which breaks the promise that "scripts can rely on these codes." *Recommendation:* either override `clap`'s error exit to 1, or give data-file errors a distinct code. Record this in the same ADR as the parser choice, and add a test for a malformed-argument exit code.
- C-5: **Major: Atomic rename breaks the synced-folder and symlink case the brief itself promotes.** *Scope:* §5 *Half-written file*; §10 *Data file location*, which says "people who keep the file in a synced folder."
    - If `habits.json` is a symlink into a synced folder, renaming a temp file over it replaces the link with a regular file. Later writes then silently stop reaching the synced copy.
    - Sync clients such as Dropbox and Syncthing can create conflict copies or race with rename-replace.
    - Using the file from more than one device brings back the "last write wins" loss as a routine event, not a rare one. This also undercuts the "no sync" non-goal.
    *Recommendation:* resolve symlinks (`canonicalize`) before choosing the temp-file directory and rename target. Either drop the synced-folder endorsement or state its risks plainly. Add a test for writing through a symlink.
- C-6: **Major: The durability claim is incomplete.** *Scope:* §5, "write to a temporary file in the same directory, flush it, then rename." Flushing a userspace buffer is not durable. Without `fsync` on the temp file, and on Linux `fsync` on the parent directory after the rename, a power loss can leave an empty or zero-length file. That is the outcome this decision exists to prevent. *Recommendation:* specify `File::sync_all()` before the rename and a directory fsync after it.
- C-7: **Major: The temp file name and its permissions are unspecified.**
    - *Scope:* §5. If the temp file name is fixed (for example `habits.json.tmp`), two concurrent commands write the same temp file. The result can be a corrupt file, not just a lost check-in, which contradicts the "rare, last writer wins" analysis. *Recommendation:* use a unique temp name (`tempfile::NamedTempFile::new_in`).
    - A new temp file gets default umask permissions. Renaming it can widen the access mode of a file the brief calls "private." *Recommendation:* copy the original file's mode onto the temp file.
- C-8: **Major: Future-dated entries already in the file have no defined behavior.** *Scope:* §2 *Time zones and travel*; §3; §5 *Hand edits*; Decision 4. Only `check` rejects future dates. A file can still contain dates later than "today" in three ways:
    - a hand edit,
    - a check-in made in London, then running `status` after flying west to New York,
    - a clock correction.
    `streaks(dates, today)` and the backward-walking oracle are not specified for this input. The oracle ignores such dates, while a run-based implementation might count them toward longest or current, so the property test could pass or fail arbitrarily depending on generator range. *Recommendation:* define the semantics, for example ignore dates after `today` for current streak and include or exclude them consistently for longest. Have the property generator include future dates.
- C-9: **Major: Case-insensitive names collide on read.** *Scope:* §6 *Case and spaces*; §5 illustrative file, where habits are keyed by name. A hand edit can produce both `"Read"` and `"read"` keys. Under case-insensitive comparison they are the same habit, and the read behavior (merge, reject, or first wins) is undefined. "Case-insensitive" for non-ASCII names is also unspecified (ASCII lowercasing, Unicode `to_lowercase`, or full case folding). *Recommendation:*
    - Treat normalized-key duplicates on read as a data-file error (exit 2) or define a merge rule.
    - Choose and document the folding method.
    - Add a test for each.
- C-10: **Major: The oracle covers only the current streak.** *Scope:* §11; Gate (a). "Walk backward one day at a time from today and count" is independent only for the current streak. The longest streak, including the backfill-merge case in §3, has no independent oracle, so the two-implementations safeguard does not cover half the output. *Recommendation:* specify an equally naive longest-streak oracle, such as checking each date as a run start and walking forward day by day.
- C-11: **Nit: The meaning of `created` is unspecified.** *Scope:* §5 file shape. It is unclear whether check-ins or backfills before `created` are allowed, rejected, or move `created` back, and whether a hand-edited `created` that is later than some check-ins is an error. If nothing reads the field, it is dead data, close to the "second source of truth" §4 warns against. *Recommendation:* define the rule or drop the field.
- C-12: **Nit: Several command edge cases are unspecified.** *Scope:* §6 command surface. Missing definitions:
    - exit code and message for `uncheck` on a date with no check-in,
    - `remove` without `--yes`,
    - `uncheck` with a future date,
    - `add` on an existing name.
    *Recommendation:* tabulate these outcomes, mirroring the idempotence rule already stated for `check`.
- C-13: **Nit: Gate coverage is narrower than the stated decisions.** *Scope:* Gate (a)–(d). There is no test that an unknown `"version"` gives exit 2 with the file byte-for-byte unchanged (Decision 7), and none for duplicate or malformed hand-edited dates (§5). *Recommendation:* add both to the gate.
- C-14: **Nit: Platform scope is implicit.** *Scope:* §5 says "on Linux and macOS the rename replaces the file in one step"; §10 covers XDG paths only. Windows support is neither stated nor excluded, and rename-over-existing behaves differently there. *Recommendation:* declare the supported platforms in Goals and Non-Goals.
- C-15: **Nit: The Objectives are partly jargon.** *Scope:* *Overview*, Assumption 6 ("hexagonal-architecture exercise"). The standard requires the objective without jargon, yet a co-equal goal is stated only in jargon. Its status is also left open ("Is the architecture practice a real goal?"). *Recommendation:* settle that question in the brief and restate it plainly, for example "practise keeping business rules separate from file and clock code."
